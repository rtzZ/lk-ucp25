# Архитектура

## Общая картина

```
Яндекс.Диск (2 публичные таблицы)
        │  каждые 48 ч, APScheduler 3.x (lifespan FastAPI)
        ▼
extract_downloader_url  — headless Chromium рендерит edit-страницу,
                          из HTML извлекается подписанный URL
download_xlsx           — скачивание через httpx (query менять нельзя:
                          подпись покрывает его целиком)
parse_*_xlsx            — openpyxl, чистые функции (юнит-тесты без файлов)
upsert_*                — полная замена данных в PostgreSQL
        │
        ▼
FastAPI (auth, students, schedule, grades) --JSON--> React (Atlassian DS)
```

При недоступности ссылок ошибка логируется (`sync_source` не пробрасывает
исключения), API продолжает отдавать последние успешные данные из БД.
Пустые `YANDEX_*_URL` — пропуск с warning.

Почему Chromium, а не API Диска: публичный `cloud-api.yandex.net` отвергает
ключи `disk.360.yandex.ru` (400), а прямые ссылки downloader'а работают только
с точной подписью из отрендеренной страницы (иначе 403). Проверка без cookies:
`GET` edit-страницы обычным HTTP-клиентом возвращает JS-заглушку без ссылок.

## Формат таблицы расписания

Файл «Расписание УЦП-25…»: парсятся только листы `N семестр` (группа
из имени файла). Листы чужих групп (напр. «ЛФТ-25 2 сем») пропускаются
с warning; группы-сироты без студентов и пар чистятся при синхронизации —
в кабинете только своя группа. Шапка:
строка 1 — дни недели (merged), строка 2 — время пар (`HH:MM-HH:MM`).
Колонка `воскресенье` есть не везде. Колонки правее воскресенья — зона
аттестаций, в пары не идёт.

Далее блоки недель: строка с датами (`datetime` в day-колонках, номер недели
в колонке A — опционален) + строки пар. Ячейка пары — многострочный текст:
`Предмет / Организация / Номер / Преподаватель` + маркеры. Парсинг
(`parse_lesson_cell`): вид — `lesson | attestation | event | deadline`,
статус — `active | cancelled (ОТМЕНА) | moved (ПЕРЕНОС)`. Первое URL
в тексте ячейки сохраняется в `ScheduleItem.link` (поле «Ссылка
на подключение»). Одиночные `Сессия/Каникулы` — служебные, пропускаются. Не-строковые ячейки
(время `22:10`, числа) — не пары, пропускаются.

## Формат таблицы успеваемости

Файл «Успеваемость сводная УЦП-25»: листы-семестры (листы `Команды…` —
не оценки, пропускаются). Строка с `ECTS` — строка заданий; шапка блока —
ближайшая merged-строка выше с названием предмета (строки формул
`ИТОГОВАЯ…/Кт…/УСПЕВАЕМОСТЬ` отбрасываются). Тип аттестации: ячейка слева
от шапки, скобки в названии `(зачет с оценкой)` или строка заданий.

Ключевые правила, выведенные по реальным данным:
- Шкалы четыре, связаны парами: итоговая 1–5 ↔ словесная
  (Отлично/Хорошо/...), баллы 0–100 ↔ ECTS (A–F/Passed). У зачётных
  дисциплин только две шкалы (баллы + зачтено). Якорь блока — колонка
  баллов («Итого»/«Всего», точное совпадение важнее префикса: «Всего за КТ»
  не якорь); итоговая — первая колонка после неё с пустой шапкой или
  «Итоговая оценка» (не «Итоговая защита»!); словесная и ECTS определяются
  по значениям, а не по шапкам (шапки врут: пустые, «ECTS» над словесной).
- Название предмета чистится от организации и преподавателя; организация
  в скобках внутри названия («... проекта (Нетология)») вырезается,
  строка остаётся. Ловушка префиксов: «Итоговая ...» начинается
  на «итого», но баллами не является — исключено явно.
- Пустая итоговая ячейка = минимальная оценка: 5-балльная → «2»
  («Неудовлетворительно», ECTS F, 0 баллов), зачётная → «не зачтено».
  Блоки со своим списком (факультатив) затрагивают только своих участников.
  Так подтягивается и будущий 3 семестр (пока весь минимальный).
- ID студентов в таблицах нет. `Student.code` — нормализованные
  «фамилия имя» (отчество игнорируется: одни и те же люди записаны то
  с отчеством, то без).
- Оценки блоков привязаны к строкам основного списка (колонка B).
  Исключение — блоки со своим списком (факультатив): колонка имён левее
  блока, почти не пересекающаяся с основным списком (порог 90%), —
  привязка позиционная. Вспомогательные списки (команды в блоке проектной
  дисциплины) игнорируются.
- Сопоставление ФИО: точное → перевёрнутое «Имя Фамилия» → нечёткое
  (difflib ≥ 0.9, покрывает ё/е и опечатки). Несопоставленное — пропуск
  с warning, дубликатов по `(student, subject, semester)` быть не должно.
- Значения оценок хранятся как у преподавателя (`5`, `зачтено`, баллы,
  разный регистр) — нормализация на отображении.

Проверено на реальных файлах: 682 записи расписания (УЦП-25 + ЛФТ-25),
797 оценок, 50 студентов, 19 предметов.

## Backend

- `db.py`: `AsyncEngine` + `async_sessionmaker(expire_on_commit=False)`,
  `get_session` — зависимость FastAPI. Связей `relationship` в моделях нет
  осознанно (ленивая загрузка падает в async) — только FK + явные select.
- Таблицы создаются `create_all` при старте (ленивый путь; Alembic подключать
  при первой эволюции схемы).
- `logging.py`: loguru `serialize=True` — каждая строка stderr это JSON;
  middleware в `main.py` пишет каждый запрос (`method/path/status/elapsed_ms`).
- Планировщик: `AsyncIOScheduler`, `add_job(_sync_job, "interval",
  hours=SYNC_INTERVAL_HOURS, coalesce=True, max_instances=1)`.
  `_sync_job` глотает все исключения (планировщик обязан переживать всё).
- Важно: APScheduler 4.x существует только в альфах на PyPI — зафиксирован
  стабильный 3.11.x (API `AsyncIOScheduler`). Документация Context7 отдавала
  API master-ветки (4.x) — не использовать без проверки установкой.

## Frontend

Vite + React 18 + TypeScript + Atlaskit (`button/new`, `dynamic-table`,
`lozenge`, `select`, `textfield`; сверено с Context7). Состояние — `useState`
без роутера (3 экрана): `Login` → вкладки `Schedule` / `Grades`.
Сессия хранится в `localStorage`. Mobile-first CSS поверх компонентов
(max-width 720). Вход — идентификация себя (фамилия+имя), пароля нет:
данные общие, вход нужен чтобы показать свои оценки.
Клик по паре открывает `@atlaskit/drawer` (композиция `Drawer` +
`DrawerCloseButton` + `DrawerContent`): детали занятия и поле «Ссылка
на подключение» (readonly + ссылка «Подключиться к паре»).
Важно: `React.StrictMode` отключён в `main.tsx` — `@atlaskit/portal` v6
теряет контент popup/drawer при двойном монтировании эффектов в dev.

## Тестирование

- `backend/tests/test_sync.py` — чистые функции парсера + мини-листы,
  собранные кодом в реальном формате (без бинарных фикстур).
- `backend/tests/test_api.py` — API на sqlite через подмену `get_session`;
  требуется `SKIP_DB_INIT=1` (иначе lifespan полезет в Postgres).
- `frontend/e2e/cabinet.spec.ts` — Playwright: вход → расписание → оценки,
  desktop + mobile 390px (проверка отсутствия горизонтального скролла).
  Требует запущенные backend (`SEED_DEMO=1`) и frontend dev.
